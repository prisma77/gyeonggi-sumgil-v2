## 실행·표시 검증

`review_scenario.py`는 명시한 주소를 다시 검색하고 접근 2회를 먼저 조회한 뒤
휴대폰의 명시적 버튼으로 공원 1회를 조회한다. 호출 상한 3회, 응답 캐시 없음.
주소가 단일 후보가 아니면 경로 조회 전에 중단한다.

```powershell
D:/Python/python.exe -B experiments/android-route-review/review_scenario.py --catalog experiments/android-route-review/misa-scenario.catalog.json
```

기존 8769 서버를 종료한 뒤 실행한다. USB 앱 연결은 `adb reverse tcp:8769 tcp:8769`.
이번 실행은 8770에 시나리오 서버를 열고 기존 앱 포트 8769에 RAM 전달만 수행하는
로컬 연결을 두었다. 전달은 경로 API를 추가 호출하거나 응답을 저장하지 않는다.

거리 조건을 응답 값으로 표시하도록 Android 화면을 수정하고,
공원 산책 거리와 주소 접근을 분리해 표시했다. 휴대폰에 APK를 설치하고 직접 확인했다.
실제 지도는 붉은 실패 경로, 1,811m, 2,850~3,150m 미달, 순환 판정 보류를 표시한다.
카카오 지도 캡처는 RAM에서 확인·표시하고 파일로 저장하지 않았다.

Python 보행 검증 117개 + bridge 15개 = **132개 통과**.
주소 접근 거리를 공원 목표에 더하지 않는 검사와 잘못된 거리 조건/범위 차단 검사를 추가했다.
Android `assembleDebug lintDebug` 성공(19초). 빌드 성공은 실제 코스 품질 통과가 아니다.

**이 시나리오의 공원 3km 요청은 현재 해결하지 못했다.**
다음 개선은 목표 거리 조건을 갖춘 호수·공원 후보 생성과 실제 순환 반복 구간 검증이다.

## 사용자 현장 피드백과 거리 재확인

사용자는 시작점이 적절하고 평소 달리는 코스와 거의 일치한다고 평가했다.
평소 코스는 약 3km로 인식하며 집 접근이 아닌 공원 순환 구간만을 요청한다고 확인했다.
이 피드백은 후보의 시작 위치·코스 모양에 대한 현장 근거다.
달리기 기록과 정확히 같은 경로를 확인한 것은 아니므로 실측 거리나 현재 모든 구간의 통행을 검증했다고 표시하지 않는다.

기존 순환 보류 4건을 분류하면 `TOUCH` 3건과 `OVERLAP` 1건이며 `CROSS`는 0건이다.
모두 순환 출발 원본 노드 `7221968198` 부근이고, 실제 API 선형 첫 약 8.01m 구간을
복귀할 때 반대 방향으로 재사용한 것으로 분석된다. 네 군데의 별도 교차를 의미하지 않는다.
현재 검증기는 짧은 출발 접근 구간이 붙은 순환과 단순 순환을 구분하지 않아 보류한다.
원본 API 경로를 잘라내거나 연결선을 생성하지 않았다. 이 진단만으로 한 바퀴 승인도 하지 않는다.
