# 선택 장소 보행망 → 실제 경로 검증 — 2026-10-09

이 문서는 최초 연결 단계의 이력이다. 이후 검사 표시 분리·전체 원본 보행망/교량 대조·목표 거리별 복수 순환 탐색과 최신 검증은 [후속 구현 기록](route-checks-and-multiple-cycles.md)을 참조한다.

최소 총 2km·2~20km 입력·명시적인 반복 순환 대안은 [총거리와 반복 계획 기록](walk-distance-and-repeat-plans.md)을 참조한다. 아래 500~5000m 범위와 초기 조회 횟수는 최초 연결 당시의 이력이다.

## 연결한 범위

경로 탭에서 실제 검색 후보를 직접 선택하고 아래 순서로 실행한다.

1. `호수 한 바퀴` 또는 `하천 왕복` 선택.
2. 목표 거리 입력. 호수는 비우면 한 바퀴이며 기본 거리로 바꾸지 않는다. 하천은 거리 입력이 필요하다.
3. `선택 장소 보행망 확보 (OSM 1회)`.
4. 원본 수역·하천 후보 선택 후 주황색 선형을 지도에서 대조.
5. `이 대상 확인 후 후보 계산`.
6. 원본 후보를 직접 선택하고 `이 입력으로 실제 경로 조회 (1회)`.

지원 범위는 호수 전체 수역 순환과 하천의 같은 길 왕복이다. 일반 공원 임의 순환은 아직 지원하지 않는다.
목표 거리는 500~5000m를 명시하고 ±10%를 원본 후보 및 API 반환 거리에서 검사한다.
집↔공원 접근은 포함하지 않으며 출발점은 확보한 원본 보행 노드다. 선택한 POI가 보행 출입구라는 가정도 하지 않는다.

## 장소·원본 확보

- Android는 현재 검색에서 받은 장소 ID만 서버에 전달한다. 임의 좌표·OSM ID를 요청으로 넣을 수 없다.
- PC는 마지막 검색의 최소 POI 필드(ID·이름·분류·좌표)를 RAM에서 최대 10분 보유한다.
  새 검색을 시작하면 이전 검색 세대와 원본 확인·후보를 폐기한다. GPS·주소·검색 거리는 보관하지 않는다.
- 장소 선택 시 공개 POI 중심의 약 1.8km 여유 범위로 Overpass에 1회 요청한다.
  OSM에 사용자 GPS를 보내지 않으며 원본은 이 단계에서 파일에 저장하지 않는다.
- JSON·server timeout 20초·memory 선언 32MiB, HTTP timeout 28초·응답 16MB·요소 60000개 한도.
  오류·부분 응답·쿼터 실패 시 자동 재시도·다른 서버·다른 장소 대체 없음.
- 수역은 완전한 닫힌 way 또는 단일 완전 outer way인 multipolygon만 지원한다. 분할·여러 outer는 확인 불가로 중단한다.
- 호수의 정확한 OSM 이름 일치와 POI 350m 이내 위치를 대조한다.
  인근 이름 없는 수역은 동일 대상이라고 판단하지 않고 최대 5개의 **확인 대상**으로만 제시한다.
  선택한 수역 경계를 지도에서 직접 확인해야 후보 계산을 실행할 수 있다.
- 하천은 동일한 이름의 river/stream way와 POI의 근접 조건을 요구한다. 다른 이름의 하천으로 바꾸지 않는다.
- 출처·ODbL·기여자 표시·수집 시각·출처 URL과 라이선스 URL을 표시한다. 수집 시각은 현장 관측이 아니다.

공개 Overpass는 이번 수동 시험에 사용한다. 운영 앱의 상시 서버로 확정한 것이 아니다.
[운영자 안내](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)는 일반 앱이 공개 인스턴스를 backend로 의존하는 경우 자체 인스턴스 운영을 권한다.
[bbox·geometry 문서](https://dev.overpass-api.de/overpass-doc/en/full_data/bbox.html)에 따라 원본 geometry를 자르지 않고 way의 실제 node ID와 좌표를 사용한다.

## 원본 후보 생성과 검증

- `SelectedNetwork`의 source provider 경계와 Android `ReviewGateway`의 두 요청을 추가했다.
  전체 앱 구조나 날씨·대기질·AI 흐름은 바꾸지 않았다. 현재는 PC loopback 검증 서버가 필요하다.
- 출발점을 POI에서 500m 이내의 보행망에서 고른다. 접근 경로가 검증됐다고 설명하지 않는다.
- footway/path/pedestrian/steps 및 명시 foot 허용 cycleway만 보행망으로 사용한다.
  foot 방향·접근 금지·원본 노드 연결을 반영하고 gate 등 barrier node, tunnel, conditional access 구간은 보수적으로 제외한다.
- 수역·하천 선형을 가로지르거나 겹치는 구간을 제외한다. bridge 태그 자체는 통행 증명이 아니며 원본·API 교량 검토 경고를 유지한다.
- 호수 경계 180m, 하천 선형 100m 안에서 원본 구간의 끝점과 중간점을 검사한다.
  이는 후보 탐색 정책이며 보행 가능성·지도 정확도의 보장이 아니다.
- 원본 way 일부만 조건을 벗어나면 해당 **실제 edge**만 제외한다. 좌표·tags는 그대로 두고 allowlist를 원본 방향 edge와 교차한다.
  가까운 노드를 붙이거나 끊어진 구간의 connector를 만들지 않는다.
- 호수는 전체 수역을 둘러싸는 단순 닫힌 원본 cycle을 찾는다. 거리 불일치 시 반복·우회를 덧붙이지 않는다.
- 하천은 원본 양방향 edge의 최단 연결을 사용해 목표 왕복 거리에 가까운 반환점을 최대 3개 비교한다.
  원본 노드 최대 200개와 실제 경유점 최대 5개로 A→B→R→B→A를 만들며 반환점·왕복 방향·거리 검사를 유지한다.
- 분석은 target segment 1500개, raw edge×target segment 400만, 필터 후 node 10000개·edge 30000개로 제한한다.
  한도 초과도 데이터 부족 상태이며 성공 후보로 표시하지 않는다.
- 원본 입력을 자동 감사한 후에만 `/route`에 등록한다. 기존 `walk_points_reviewed` 플래그는 이 경로에서
  **자동 source audit만 완료**한 의미로 설정하며 사람·현장 검증이 아님을 별도 표시한다.
- 확보한 보행망은 별도 10분 유효기간을 갖는다. 앞선 검색의 만료가 방금 확보한 원본을 즉시 무효화하지 않도록 했다.
  새 검색·새 원본 확보·새 후보 계산은 이전 capability ID와 경로 후보를 무효화한다.
- 실제 API 응답의 장소 ID, 경유점 순서·거리, 출발/복귀, 원본 corridor, 거리, 반복·역방향, 전체 수역 순환을 검사한다.
  응답의 step을 개별 선으로 표시하고 구간이 끊기면 임의로 잇지 않는다.
- 원본 미리보기는 주황색이며 실제 API 보행 경로와 구분한다. 모든 결과는 현재 통행·추천 미승인이다.
  선형 통과와 현재 출입 가능성·안전성·추천 품질을 동일하게 취급하지 않는다.

## 검증

- Python 장소·bridge·선택 원본 테스트 41개 통과. 기존 경로 알고리즘 테스트 117개 통과.
  임의 장소/좌표, 이름 불일치, 원본·선택 만료, 새 검색의 후보 폐기, 방향 금지·barrier·conditional,
  없는 보행망, 원본 edge 보존, 3km를 반복으로 채우지 않음, 잘못된 API 거리의 실패 처리 포함.
- Kotlin 기존 단위 테스트 52개 통과(수동 유료 Gemini 실험 2개 건너뜀), APK build·lint 성공.
- 저장된 서로 다른 지역의 독립 원본으로 미사 약 1854.7m 호수 cycle과 오산천 약 2549.6m 왕복 후보를 확인했다.
  이는 source 후보이며 실제 API 결과가 아니다. 오산천의 좌표·코스를 알고리즘에 하드코딩하지 않았다.
- Xiaomi에서 실제 검색→미사 선택→새 OSM 원본→수역 지도 대조→후보 선택→실제 API 조회 연결을 확인했다.
  새 원본 후보는 1901m로 이전 파일의 source 길이와 달랐으며, 실제 API는 **1702m / 1603초 / step 23개**를 반환했다.
  경유점 차이 0.2·0.6·0.5·1.1·0.3m, 방문 순서 PASS_WITHIN_30M, 동일 선분 반복 27.1m.
  순환은 응답 step 연결과 수역 통과·교량·반복 검토가 남아 **판정 보류**했다. 한 바퀴 통과·추천 승인으로 보고하지 않는다.
- 같은 호수에서 3000m 입력 시 원본 거리 범위 불일치 안내를 확인했고 도보 API 호출 없이 중단했다.
  이후 사용자가 명시적으로 거리를 비우고 한 바퀴 후보를 계산하는 흐름으로 조회했다.
- 최신 APK·서버에서 망월천 검색→OSM 이름·위치 대조→원본 선형 지도 확인→3km 왕복 후보→실제 API 조회를 확인했다.
  원본 후보 2997.4m·약 2920m·약 2871m 중 첫 후보만 API로 검증했으며 미조회 후보와 API 품질 순위를 비교하지 않았다.
  실제 API **3000m / 2818초 / step 18개**, 경유점 차이 0.6·0.4·3.6·0.4·0.6m.
  거리 조건 2700~3300m 통과, 반환점 차이 3.6m, 원본 보행로 최대 차이 8.1m,
  step 끝점 최대 차이 0.0m(표시 반올림), 판정 보류 step 0개, 역방향 이동 갈 때/올 때 각 0.4m.
  동일 선분 반복 1496.9m는 왕복에 필요한 재방문을 포함한다. 방문 순서·왕복 선형 검사 통과,
  inspection 실패·추가 검토 코드 없음. 원본 audit의 현재 통행 미확인과 **추천 미승인**은 유지한다.
- 실제 시험 총 호출: 카카오 장소 6회, OSM 3회, 도보 2회, Gemini 0회.
  첫 세션은 장소 3·OSM 2·도보 1회(두 번째 OSM은 하천 확보만 실행),
  검색/원본 유효기간 수정 후 새 세션은 장소 3·OSM 1·도보 1회다. 세션별 계수와 전체 시험 합계를 구분한다.
- 실기기 AndroidRuntime FATAL EXCEPTION 0건. 같은 최신 APK를 Android Studio x86 에뮬레이터에 설치해
  SDK 지원 제한 안내와 크래시 없음도 확인했다. 에뮬레이터에서 실제 카카오 지도·경로가 검증됐다고 보고하지 않는다.

남은 품질 문제는 호수 응답의 step 연결·교량 및 전체 수역 순환 검증, 출발 보행 노드까지의 접근,
현장 출입·통행 확인과 여러 실제 API 후보의 비교다. 위 연결 기능 완료를 이 문제들의 해결로 설명하지 않는다.

이후의 연결 차이·수역/교량 근거 표시와 독립 모드 시험은 [호수 순환 판정 근거 개선](lake-validation-evidence.md)에 기록했다.
위 검증은 연결 기능 단계의 이력이며 후속 시험 합계를 섞지 않는다.

## 실행

```powershell
python -B experiments/android-route-review/bridge.py --catalog experiments/android-route-review/unseen-sites.catalog.json --max-calls 2 --max-search-calls 6 --max-source-calls 3
adb reverse tcp:8769 tcp:8769
```

주변 검색 버튼은 카카오 장소 API 3회, 원본 확보 버튼은 OSM 1회, 실제 경로 버튼은 도보 API 1회다.
대상 확인·후보 계산·후보 선택은 API를 호출하지 않는다. Gemini 호출은 없다.
호출 한도는 서버 세션별 시험 제한이며 계정 전체 요금·쿼터와는 별개다.
