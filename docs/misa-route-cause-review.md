# 미사 호수 경로의 보류·실패 원인 검토 — 2026-10-09

## 결론

현재 화면의 “추천 미승인”은 미사 코스에 대한 개별 승인 결과가 아니다.
검증 서버의 모든 응답에 붙는 실험 단계 상태와, 실제 경로 검사 결과가 함께 표시되어 오해를 만들었다.
실제 검사에서 멈추는 원인은 step 연결의 수치 기준, 선택 순환선과 다른 보행로 이용,
교량에서의 수역 교차, 짧은 재방문이다. 3km 요청에는 별도로 후보 탐색의 제약이 있다.

앱의 판정 기준을 낮추거나 경로를 보정하지 않고 검토했다. 코드·공식 문서·새 실제 응답을 대조했으며
API 응답과 원본 geometry는 RAM에서만 분석했다. 앱 기능 코드는 이번 검토에서 바꾸지 않았다.

## 같은 입력의 실제 API 비교

카카오 장소 검색에서 이름이 미사호수공원이고 주소가 경기 하남시로 시작하는 단일 후보를 확인했다.
앞서 지도 대조를 마친 수역 way 593638310을 **이 사례의 명시적인 실험 입력**으로 선택했다.
일반 알고리즘에 이 ID를 하드코딩하지 않았다.
OSM 원본을 한 번 확보하고 생성된 동일 후보·동일 출발/도착·동일 경유점 5개로 두 모드를 순서대로 조회했다.
현재 GPS와 Gemini는 사용하지 않았다. 목표 거리는 명시하지 않은 한 바퀴 시험이며 3km 통과 시험이 아니다.

| 원본 후보 길이 | 1901.2m | 동일 원본·입력 |

거리 비율은 10m 이하 간격의 검사점을 사용한 기하 비교다. 원본의 현장 정확성·통행 가능성·공원 내부 여부를 증명하지 않는다.
이번 요청 합계는 장소 1회·OSM 1회·도보 2회·Gemini 0회다. 이전 시험의 호출 합계와 구분한다.

## 1. 미승인 문구는 계산된 코스 판정이 아님 — 확인

`bridge.py:221`은 실제 inspection 결과와 관계없이 `recommendation_quality="NOT_ACCEPTED"`를 반환한다.
`VerifiedRouteScreen.kt:302`도 이 고정 값을 기대하고 `:305`에서 조회 완료에 미승인 문구를 붙인다.
이는 실험용 서버의 보호 상태이며, 정상 선형이 곧 실제 통행 확인이라는 가정을 하지 않기 위한 것이다.

따라서 “41cm 차이 때문에 추천 승인을 못 받았다”는 설명만으로는 정확하지 않다.
그 차이를 해결해도 현재 서버는 미승인을 반환한다.
실험 단계, 선형 검사 통과/실패/보류, 현재 통행 미확인, 목표 조건 충족 여부를 분리해 표시해야 한다.
실제 통행 미확인 경고를 없애는 방식으로 이 문제를 해결해서는 안 된다.

## 2. 1mm 기준이 전체 순환 분석을 막음 — 확인, 물리적 원인은 미확정

`validate_lap.py:7`의 수치 동등성 기준은 0.001m다. `:90`의 검사에서 이를 초과하면
`LAP_DISCONNECTED_GEOMETRY`를 반환하고 전체 수역 포함·단순 순환 분석을 수행하지 않는다.

- 실제 응답은 13→14구간에 0.410247m 차이가 있다.
- 두 인접 선분은 실제로 교차하지 않았고, 한쪽 끝점이 다른 step의 선 위에 놓인 것도 아니다.
  겹친 선을 잘못 읽은 사례는 이번 대조에서 확인되지 않았다.
- 다음 step의 안내 시작 좌표는 다음 path 시작점과 같고 이전 path 끝점과 0.410247m 떨어져 있었다.
  공식 문서에 따라 `properties.x/y`를 확인했지만 별도의 실제 연결 geometry를 찾지는 못했다.
- 양 끝점의 가장 가까운 OSM 보행 way는 모두 989022882(highway=footway)였다.
  원본 선과의 차이는 각각 0.8936m·0.6638m다.

API 선형의 불연속과 수치 검사 중단은 확인됐다. 실제 길이 끊겼는지, 공급자 좌표 표현·분할의 차이인지는 미확정이다.
같은 OSM way에 가까운 것만으로 동일 링크·방향·층·장애물·현재 통행을 증명하지 않는다.
41cm를 부동소수점 오차로 확정하거나, 1mm를 임의로 1m로 바꿔 가상의 연결선을 넣을 근거는 없다.

개선 방향은 실제 원본 edge·연결·방향·layer·barrier 근거로 연결 가능성 상태를 추가하고,
API geometry 불연속과 물리적 보행 불가 판정을 구분하는 것이다. 원본/API 선형은 그대로 유지해야 한다.

## 3. 보행로 불일치 검사의 기준이 선택한 순환선 하나임 — 확인

`probe.py:226`은 선택한 `reference_walkway`의 20m 이내 비율을 계산하고 90% 미만이면 실패시킨다.
이는 **선택한 원본 코스와의 일치도**다. 선택 장소의 모든 보행로에서 이탈했는지 검사하는 것과는 다르다.

큰길 우선은 이 기준에서 68.82%로 실패했다. 그러나 필터 전 보행 원본 전체와는 99.14%가 20m 이내였다.
21~23번 step이 가까운 원본은 way 918087940(highway=cycleway, foot=designated)다.
22번 step은 약 344.57m이고 선택 순환선 일치도는 0%였지만 해당 원본 선과 가장 크게 벗어난 검사점도 약 6.04m였다.

따라서 “요청한 원본 순환선과 달라졌다”는 결과는 타당하다. 이를 보행 불가나 다른 공원 선택으로 설명할 근거는 부족하다.
필터 후 일치도도 95.67%이며, 남은 이탈과 장소 범위·전체 수역 순환 여부는 별도 확인이 필요하다.
20m 근접 자체를 통행 검증으로 승격해서는 안 된다.

개선 방향은 선택 코스 유지, 확보한 보행망 이용, 확인한 장소/수역 범위, 전체 순환을 독립된 검사로 두는 것이다.
API의 코스 변경도 제약 위반인지 같은 장소의 유효한 대안인지 구분해야 한다.

## 4. 교량을 사용하는 API와 수역 교차를 제외하는 후보 정책의 차이 — 확인

두 모드 모두 15번 step에서 OSM 수역 내부 검사점 1개가 있었고 경계 안쪽 최대 거리는 3.846m였다.
그 검사점은 원본 보행 교량 5m 이내에 있다. 가장 크게 벗어난 검사점의 가까운 원본은
way 921528255(bridge=yes, highway=footway, layer=1)이고 차이는 0.0353m다.

독립적으로 저장된 OSM fixture에서도 이 교량 way와 대상 수역 경계의 교차 2개를 확인했다.
이 결과는 저장된 원본의 기하 관계이며 새 API 응답이나 현재 교량 통행 증명이 아니다.

`selected_network.py:139`와 `plan_source_cycle.py:44` 부근은 전체 수역을 가로지르는 edge를 후보 순환에서 제외한다.
반면 API는 이 교량을 사용했다. 단순 수역 내부 점 검사가 교량 통행 가능성과 구분되지 않으면 불필요한 경고가 될 수 있다.
다만 교량으로 수역 일부를 잘라 가는 코스가 “전체 대상 수역 한 바퀴” 요청을 만족하는지는 별개의 문제다.

개선 방향은 교량 원본·연결·layer·접근 제한을 확인하고, 통행 가능성 근거와 전체 수역 포함 여부를 각각 판정하는 것이다.
교량 태그만으로 승인하거나 교량 때문에 전체 순환 조건을 생략하지 않는다.

## 5. 실제 짧은 왕복은 존재하며 원인 분류가 부족함 — 일부 확인

두 모드의 8번 step 선분을 9번 step에서 재방문해 27.1m가 집계됐다.
가까운 원본은 보행 way 773716021이며 첫 끝점 차이는 약 0.5873m다.
원본과 매우 가까운 실제 선분의 재방문이므로 지도 마커 오차만으로 생긴 경고는 아니다.

다만 경유점의 API 링크 선택, 필요한 접근 가지, 불필요한 우회 중 어느 원인인지는 이번 검사로 확정하지 못했다.
`plan_source_cycle.py:94~114`는 교량 노드를 피하고 거리 구역별 ground 노드를 고르지만
하천에서 쓰는 `select_network_anchors.py`의 교차로·경로 분류 변경점 주변 입력 제외를 적용하지 않는다.
이 차이는 입력 모호성 위험이며 이번 27.1m의 확정 원인은 아니다.

개선 방향은 반복 구간을 실제 경유점·leg 경계·출발 접근 구간과 대조해 필요한 가지와 우회를 분류하는 것이다.
전체 경로를 무조건 단순 다각형으로 요구하면 정상적인 접근 가지도 모두 보류하므로 순환 본체와 가지를 구분해야 한다.
진단만으로 반복 구간을 삭제하거나 거리를 숨기지 않는다.

## 6. 3km 후보를 탐색하지 않고 최단 순환 하나만 거리 검사함 — 확인

`plan_source_cycle.py:87`은 검증된 원본 순환 중 가장 짧은 것을 고른다.
`selected_network.py:168~174`는 이 후보 하나를 만든 뒤 입력 거리의 ±10%와 비교해 불일치하면 중단한다.
거리 목표는 cycle 탐색 자체에 전달되지 않는다.

따라서 이번 원본 후보 1901.2m가 3km 범위를 벗어난다는 사실은 확인됐지만,
다른 원본 edge로 구성된 적절한 3km 공원 순환이 없다는 뜻은 아니다.
현재 지원하는 전체 수역 순환과 사용자가 요청한 공원 내부 3km도 동일한 조건으로 취급해서는 안 된다.
호수 주변 180m 후보 필터, 단일 전체 수역 경계, 최단 cycle 하나의 탐색이 가능 후보를 제한한다.

개선 방향은 공원 내부 거리 요청과 명시적인 수역 한 바퀴를 구분하고,
목표 범위에 맞는 여러 실제 edge cycle을 제한된 탐색으로 비교하는 것이다.
목표를 맞추려고 동일 cycle을 반복하거나 불필요한 가지를 붙이지 않는다.

## 수정 우선순위와 완료 기준

1. 실험 단계 표시와 개별 검사 결과 분리. 정상·실패·보류가 “미승인” 하나로 보이지 않아야 한다.
2. 원본 순환선 일치도와 전체 보행망·장소 범위 검사 분리. 알려진 보행 대안도 원인을 구분해야 한다.
3. 연결 차이·교량·짧은 재방문의 독립 근거 대조. 실제 geometry를 바꾸지 않고 확인된 것과 미확정을 표시해야 한다.
4. 순환 본체/접근 가지 분리와 거리 목표를 반영하는 복수 cycle 탐색. 공원 구간만의 거리로 비교하고
   목표를 만족하는 후보를 확보하지 못했을 때 탐색 한계·데이터 한계를 명시해야 한다.

## 검증의 범위

이번 작업은 원인 검토다. 앱 코드·검사 기준 변경, 재빌드·재설치·실기기 품질 통과를 수행했다고 보고하지 않는다.
최단·큰길 우선의 실제 응답 각 1회를 같은 원본/입력으로 비교했고 원본 edge 교량 관계를 별도로 확인했다.
현재 통행·공사·안전·3km 공원 코스 존재 여부는 확인하지 않았다. 특정 지도 제공자만의 문제로 단정하지 않는다.

[카카오 공식 REST API 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api)는 경유점 최대 5개,
최단/넓은 길 우선 옵션, step.path.points 및 step.properties.x/y(단계 시작점)를 정의한다.
이번 확인에서 geometry 끝점 일치 정밀도나 교량 현재 통행을 보증하는 문서 근거는 확보하지 못했다.
