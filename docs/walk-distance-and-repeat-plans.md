# 총 산책 거리와 반복 순환 계획 — 2026-10-10

선택 장소의 원본 보행망 후보에 총거리와 명시적인 바퀴 수를 연결했다. 집↔장소 접근 거리는 포함하지 않는다. 반복은 검증된 한 바퀴를 여러 번 걷는 계획이며 기본 코스의 오류를 고치는 수단이 아니다.

## 입력과 탐색

- 거리 입력은 2,000~20,000m. 원본 후보와 실제 API 거리 모두 목표 ±10%를 검사하며 총 2,000m를 하한으로 둔다. 예를 들어 2km 요청에 1.9km 결과는 통과하지 않는다.
- 호수 거리 입력을 비우면 한 바퀴 의미를 유지한다. 기본 2km로 바꾸거나 자동으로 두 바퀴를 제안하지 않는다. 실제 한 바퀴가 2km 미만이면 최소 산책 거리 조건 불충족을 별도로 표시한다.
- `한 바퀴로 부족하면 반복 순환 대안 포함`은 기본 OFF. 선택한 경우에만 2~10바퀴 계획을 탐색한다. 하천은 이번 단계에서 기존 같은 길 왕복과 총거리 검사만 지원한다.
- 목표에 맞는 단일 순환 원본 후보를 우선한다. 부족하면 `총 목표 / 바퀴 수`를 기본 한 바퀴 목표로 삼아 같은 보행망에서 완전한 수역 순환을 탐색한다. 후보에 원본 한 바퀴 길이·횟수·총 예상거리를 함께 표시한다.
- 단일 순환 원본 후보가 있으면 이번 탐색은 종료한다. 이후 실제 API 검사에서 그 후보가 실패했을 때 반복 대안을 자동으로 재탐색하는 흐름은 아직 없다.
- 반복 탐색은 공유 20초, 개별 탐색 최대 6초, 최대 3개 결과로 제한한다. 반복 OFF 또는 거리 없는 한 바퀴는 기존 10초 한도다. 모든 바퀴 수와 코스를 빠짐없이 찾는 알고리즘이 아니며 탐색 한도 도달을 코스 부재로 단정하지 않는다.
- 20km와 10바퀴는 현재 시험의 운영 한도다. 확보한 원본 범위도 기존 POI 주변 약 1.8km 여유 범위로 유지한다. 더 먼 단일 코스나 하천 길이가 이 원본에 있다고 가정하지 않는다.

## 실제 경로와 판정

1. 기본 한 바퀴에 대해 실제 Routing API를 호출한다. 기존 입력 구조에 따라 1회 또는 분할 2회이며 요청당 경유점 최대 5개다. 반복 횟수만큼 재조회하지 않는다.
2. 반환된 기본 경로의 장소·보행망·경유점·출발/복귀·수역 둘레 순환·반복·교차 조건을 기존 검사기로 확인한다. 반환 선을 복제하거나 누락 구간을 연결하지 않는다.
3. 실제 API 한 바퀴 거리 × 명시된 바퀴 수로 총 예상거리를 계산한다. 원본 그래프 길이를 실제 API 거리 대신 사용하지 않는다. API 거리 없는 응답은 총거리 평가 보류다.
4. 기본 코스의 실패·보류를 산책 계획에도 전달한다. 계획된 두 바퀴는 기본 코스 내부의 불필요한 되짚기와 구분한다. 미사 기본 경로의 되짚기·교차가 반복 계획이라는 이유로 통과하지 않는다.
5. 기본 선형 검사와 산책 계획 검사를 지도 위에 따로 표시한다. 지도는 기본 한 바퀴만 표시하고 결과에는 `API 한 바퀴 × N = 총 예상거리`를 적는다. 이 수치는 총거리 실측이 아니다.

`walk_plan_policy.py`가 총거리 정책을 담당하고, `selected_network.py`가 원본 후보에 계획을 붙인다. `bridge.py`는 실제 기본 경로 검사 후 `walk_plan_validation`을 반환한다. 기본 검사 통과와 총거리 충족을 확인해도 현재 출입·통행은 별도 미확인이다. 추천 품질을 자동 승인하지 않는다.

최소 총 2km 기준은 선택 장소의 새 산책 계획에 적용한다. 기존 카탈로그의 짧은 디버그 시험 코스는 비교 자료로 유지하며 추천 코스로 취급하지 않는다.

## 검증

- Python 214개 통과: 기존 경로 검사 145개, 서버·장소·선택 보행망·새 정책 및 통합 검사 69개.
- 새 정책 11개, 통합 13개로 10km→5km×2, 반복 OFF, 거리 없는 한 바퀴, 최소 2km, 20km·4바퀴, 기본 실패·보류 전달, 실제 거리 사용, 경로선 미복제, API 1/2회 비용 유지 및 공유 탐색 한도를 검사했다. 이 사례는 합성/모의 데이터 검사이며 실제 장소의 5km 코스 확보를 뜻하지 않는다.
- Kotlin 55개 통과, 수동 유료 Gemini 검사 2개 건너뜀. `testDebugUnitTest assembleDebug lintDebug` 성공, lint 오류 0개·경고 11개.
- Xiaomi 실기기에서 미사호수공원을 직접 검색·선택하고 새 OSM 수역을 지도에서 대조한 뒤 10km 입력과 반복 옵션을 사용했다. 원본 후보는 `3387m × 3 = 10162m`, `3393m × 3 = 10179m`, `3482m × 3 = 10446m`였다. 이는 원본 예상거리다.
- 첫 후보의 기본 한 바퀴에 실제 카카오 SHORTEST 분할 요청 2회를 수행했다. API 반환 합계 **3046m / 2889초 / 44구간**, 산책 계획은 **3046m × 3 = 9138m 예상**으로 총거리 조건 9000~11000m를 충족했다. 실제 총 9.138km를 걸어 측정한 것은 아니다.
- 경유점 순서 통과, 최대 차이 10.7m, 전체 원본 보행망 대조 100%였다. 그러나 기본 코스 내부 동일 선분 되짚기 **402.4m**, 구간 연결 차이 최대 **1.433m**, 수역 내부 대조점 **5개**의 연결 교량 근거 미확정, 선택한 원본 순환선 일치도 **83%**가 남았다. 기본 선형·호수 순환·산책 계획 모두 **판정 보류**를 유지했다. 반복 횟수가 검사 문제를 면제하지 않았고 추천 승인도 하지 않았다.
- 이번 실기기 시험 비용은 장소 검색 1회, OSM 확보 1회, 도보 API 2회, Gemini 0회. 응답·좌표·화면 이미지는 RAM에서만 확인했다. 빌드 성공 및 정책 검사 통과는 실제 추천 품질 통과와 별개다.
- 거리·반복 옵션을 바꾸면 이전 후보와 경로 결과를 지우고 재계산 안내를 표시한다. 유효하지 않은 거리의 후보 계산은 비활성화한다.
- 실기기에서 1999m의 후보 계산 비활성화, 20000m의 후보 계산 활성화, 빈 거리의 한 바퀴 계산 활성화 및 반복 옵션 비활성화를 확인했다. 이 입력 경계 검사는 후보 계산이나 외부 API 요청을 추가로 실행하지 않았다.

앞선 미사 3km 후보 탐색·실제 API의 단축과 반복 문제는 [미사 거리 탐색 수정 기록](misa-distance-search-fix.md)을 참조한다.
