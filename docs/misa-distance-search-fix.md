# 미사 3km 후보 누락 개선 — 2026-10-10

## 확인한 원인과 수정 범위

데이터가 없다는 결론을 내릴 근거는 없었다. [직전 시험](route-checks-and-multiple-cycles.md)은 24회의 제한된 edge 제외 탐색에서 1,830~2,118.9m만 검사했다.

1. 최단 순환의 edge를 제외해 다시 최단 순환을 찾는 탐색은 작은 대안에 몰렸다. 동일 원본·동일 호숫가 180m 제한에서 순환의 실제 arc를 교체하고 조합하면 2,700~3,300m 원본 cycle을 확보했다.
2. 거리 구역별 8개 원본 노드에서 5개를 고르는 입력은 긴 굴곡을 놓쳤다. 실제 API는 첫 개선 후보 약 2.8km를 최단 1,799m·큰길 우선 1,837m로 단축했다.
3. API가 경유점을 방문하는 것과 선택한 전체 원본 코스를 따라가는 것은 다르다. 경유점 순서 통과만으로 코스·거리 통과를 판단하지 않는다.

특정 공원 좌표·way ID를 알고리즘에 넣거나, buffer를 무조건 늘리거나, 반복으로 길이를 채우지 않았다. 기존 원본 보행 적격성·금지 방향·수역 교차 제외·전체 수역 포함 검사를 유지한다. 아래 미사 ID는 이전에 지도 대조한 독립 사례 입력이고 일반 로직에는 하드코딩하지 않았다.

## 새 탐색과 요청 입력

- 실제 원본 연결 구간 사이의 대안을 탐색하고, 순환의 다른 노드 재방문을 금지한다. 대안도 전체 수역을 둘러싸는 단순 cycle 검사 후 사용한다.
- 기본 한도: 순환 확장 24회·대안 path 256회·graph heap 작업 20만 회·전체 후보 계산 10초. 최대 3개 결과이며 전수 탐색이나 최적 코스를 보장하지 않는다.
- 최대 64개 원본 ground 노드 pool에서 실제 보행 graph의 최단 길이와 원본 arc 길이 차이를 계산한다. 경유점으로 보존하기 어려운 구간을 우선 반영한다. 직선 chord를 보행 경로로 쓰지 않는다.
- 입력 분석은 heap 100만 회 및 남은 계산 시간 안에서 제한한다. 숫자는 원본 graph 분석이며 실제 API 길이 보장이 아니다.
- 5개 경유점으로 원본 거리를 충분히 보존하지 못하는 후보는 두 요청용 원본 지점을 선택한다. 요청 1과 2는 동일한 원본 노드를 분할 출발·도착으로 사용하며 각각 경유점 5개 이하이다. 전체 요청 지점은 분할 지점 포함 11개다.
- 앱 후보와 조회 버튼에 **API 2회**를 명시한다. 한 번의 버튼 실행에서 두 요청을 순서대로 수행하며 요금·쿼터도 두 호출 기준이다. 전부 필요한 호출 예산을 확인한 뒤 첫 요청을 보낸다.
- 거리·시간은 두 실제 반환 값의 합이다. 각 응답의 leg/step을 그대로 보유해 함께 검사하고, 구간 차이를 선으로 연결하지 않는다. 첫/두 번째 요청 실패 시 부분 경로를 완성된 순환처럼 표시하지 않는다. 자동 재시도 없음.
- 거리를 비운 한 바퀴와 하천 왕복 요청은 기존 동작을 유지한다.

## 실제 요청 대조

최신 원본의 첫 후보(약 3,088m)를 5개 경유점으로 개선해 조회하면 최단 **2,509m**, 큰길 우선 **2,809m**였다. 큰길 우선은 동일 선분 반복 **484.2m**와 수역 grid 감싸기 0%라는 진단이 나와 좋은 순환으로 판단할 수 없었다. grid는 진단이며 단독 승인 기준이 아니다.

저장된 독립 원본의 3,283.3m 후보를 두 요청으로 시험했다. 단순한 12개 구역 입력은 합계 **2,547m**였다. 원본 graph의 단축 손실을 줄인 입력은 실제 합계 **2,929m·2,673초**였으며 목표 거리 범위 안이다. 다만 반복 **183.5m**, 선형 교차 54건 및 일부 수역 감싸기 진단이 남아 **순환 판정 보류**다.

새 OSM 원본으로 최종 서버 연결을 시험한 첫 후보는 합계 **2,699m·2,503초**였다. 하한 2,700m보다 1m 짧아 **거리 실패**로 유지했다. 반복 **393m**·교차 검토도 남는다. ±10% 기준을 완화하거나 성공 사례만 골라 완료로 보고하지 않는다.

원본 경로와 실제 API 경로가 달라질 수 있으며 OSM park 경계도 별도 대조가 필요하다. 저장 원본의 초기 2.8km 후보들은 약 17~20%가 이름 일치 OSM park polygon 밖이었다. 호숫가 180m 범위는 공원 내부 보장이 아니다. 집↔공원 접근을 더해 길이를 맞추지 않았지만, 공원 내부 전용 코스라고 승인할 근거는 아직 부족하다.

실기기 연결 및 최종 검사 결과는 아래에 기록한다. 새로운 OSM/API 원본·지도 이미지는 RAM에서만 검사하고 저장하지 않았다. Gemini 호출은 없다.

## 최종 실기기 시험과 완료 범위

- Xiaomi의 새 검색→미사 선택→새 OSM→명시적으로 확인한 수역→3,000m 계산을 연결했다. 3,088 / 3,079 / 3,108m 원본 후보 3개를 표시했다. 각 후보에 API 2회, 조회 버튼에 2회를 표시했다.
- 세 번째 3,108m 후보만 최단 모드로 두 요청 조회했다. 각 요청의 경유점 5개 이하, 동일 원본 분할 지점, 전체 동일 출발·도착을 유지했다.
- 실제 반환 합계 **2,785m·2,595초·step 34개**, 호출 2/2. 거리 2,700~3,300m와 방문 순서 조건 통과. 보행망 대조 100%, 선택 순환선 대조 90.2%, step 및 출발/복귀 차이 0.0m(표시 반올림).
- 동일 선분 반복 **416.2m**와 자기 접촉/교차, 수역 내부 표본 1개(경계 안쪽 최대 0.031m, 연결 교량 미대응)의 검토가 남아 최종 결과는 **판정 보류**다. 노란 선·거리 통과·현재 통행 미확인을 실제 화면에서 확인했다. 2,785m에는 반복 구간이 들어 있으므로 이 값을 양질의 독립된 순환 거리라고 설명하지 않는다.
- 원본 후보 누락과 긴 코스를 표현하지 못하는 입력 연결은 개선했다. 불필요한 반복이 없는 실제 API 순환, 공원 경계 및 현재 출입 확인은 미완료다. 이 문제까지 해결됐다고 보고하지 않는다.
- Python 145개(경로·입력) + 45개(장소·서버), 총 **190개 통과**. Kotlin **55개 통과**, 수동 유료 Gemini 시험 2개 건너뜀. APK 빌드·lint 성공(오류 0·경고 11), 최종 APK 설치, 현재 실기기 PID crash record 0건.
- 검사는 원본 보존·단순 전체 수역 순환·대안 조합·금지 방향·계산 한도·분할 요청 예산 사전 확인·요청당 경유점 한도·원본 step 유지·두 번째 요청 실패 시 부분 경로 폐기를 포함한다.
- 이번 작업의 실제 호출: 장소 6회·OSM 4회·도보 12회·Gemini 0회. 최종 실기기 세션은 장소 3회·OSM 1회·도보 2회이다. 실패/중간 비교 시험도 포함했으며 이전 작업 합계와 섞지 않는다.
